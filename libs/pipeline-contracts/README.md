# Pipeline contracts

Pure validation and payload construction for the gateway and future service consumers. This library performs no rule matching, spatial indexing, geometry intersections, network calls, or message delivery.

The unified gateway uses **FindAir** (`FindAirPipelineContract`), **DeepWisdom** (`DeepWisdomPipelineContract`) and **SarAtc** (`SarAtcPipelineContract`). All three accept arbitrary ExtraData objects and preserve every key and JSON value under `extraData` in the outgoing body. DeepWisdom's named settings are optional; supplied values also populate the corresponding existing top-level fields. There is no required ExtraData field schema for these contracts. Empty/omitted objects add no extra property.

The registered contract IDs are `FindAir`, `DeepWisdom` and `SarAtc`, with exact casing. Custom catalogs must use these names.

Projection records type errors for pipeline-specific metadata in `PipelineDispatchContext.InputFieldErrors`. `ValidateContext(context, runParams)` checks only fields consumed by that run: FindAir checks its image metadata, while DeepWisdom checks relationship fields when `run_every_other_image` is true. The common input parser validates the fields required for rule matching.

`PipelineContractRegistry` resolves explicitly registered contract IDs using ordinal comparison. Unknown IDs fail resolution. The gateway registers `FindAirPipelineContract` as `FindAir`, `DeepWisdomPipelineContract` as `DeepWisdom` and `SarAtcPipelineContract` as `SarAtc`. Pipeline contracts use unversioned IDs.

One FindAir run-parameter object describes one tenant dispatch:

```json
{
  "tenantId": "tenant-a",
  "algorithmNames": ["FindAir", "Rpn"],
  "tilingConfigs": [
    {
      "tileSizeWidth": 500,
      "tileSizeHeight": 500,
      "tileOverlapWidth": 10,
      "tileOverlapHeight": 10
    }
  ]
}
```

All shown fields are required. Unknown or duplicate properties, empty collections, duplicate/unsupported algorithm names, numeric strings, and invalid tiling dimensions are rejected. Zero overlap is valid. Algorithm parsing and tiling validation reuse the common DTO contracts.

`ValidateRunParams`, `ValidateExtraData` and `ValidateContext` return field-level errors. `BuildPayload` validates its inputs again and throws `ArgumentException` on failure. Each contract validates only its own required event data. Contexts contain a caller-assigned task identity; the caller must keep their `JsonElement` alive while calling the contract (or supply a clone).

`OverlayDispatchContextFactory.Create(taskId, ruleId, overlay)` projects the flat update-overlay JSON (`id`, `photoTime`, `roiFootprint`, and other fields) into the shared context. It never substitutes `footprint` for `roiFootprint`. DeepWisdom does not require FindAir's image dimensions, image URL or grid URI. Missing FindAir values are rejected by FindAir's context validation. This projection is a payload-building helper; it does not consume messages, match rules or decide the selected ROI for FindAir.

The FindAir payload preserves the existing gateway's ordered JSON body, including singular `algorithmName` as an array and exact `gridURI` spelling. All tiling configurations remain in that tenant's body. Attributes are `algorithmName` (comma-joined names) and `tenantId`; these describe metadata for protocol adapters. Task IDs are supplied by the caller, not generated by the contract.

`PipelinePayload` also has optional typed `RabbitMqAttributes`. FindAir supplies `findair-contract-version` as an **integer** with value `1` in this dictionary to preserve the existing downstream wire contract. This marker is independent of unversioned pipeline and contract IDs. These attributes are contract output only; the library does not execute transport mapping or delivery.

`BuildPayload` accepts per-pipeline `extraData` as an arbitrary JSON object. Both contracts include nonempty data under the body's `extraData` property, preserving names and JSON types. It cannot override existing body fields or headers. Omitting the object or supplying `{}` adds no `extraData` property.

## DeepWisdom

One DeepWisdom run-parameter object describes one selected rule's mission request:

```json
{
  "customer": "replace-me-customer",
  "profile_name": "replace-me-profile",
  "hebrew_rule_name": "replace-me-mission",
  "algorithm_name": "replace-me-algorithm",
  "priority": 1,
  "username": null,
  "run_every_other_image": false,
  "should_check_in_vip": false
}
```

The optional `profile_name`, `hebrew_rule_name` and `username` accept strings or null. The other fields are required, with the shown JSON types. `algorithm_name` is one string and does not use FindAir's algorithm enum. `priority` is a 32-bit integer without an invented business range. Unknown and duplicate run parameters are rejected. These are the payload-relevant fields, not the entire stored rule document: matching conditions and rule metadata remain outside this contract.

DeepWisdom's `ExtraData` can include these optional settings alongside any custom fields:

```json
{
  "XUserName": "replace-me-user",
  "Origin": "replace-me-origin",
  "QueueType": "replace-me-queue-type",
  "SaveDetections": true
}
```

None of these settings is required. Every supplied property is preserved under `extraData`, including custom fields. Known settings additionally populate the corresponding top-level fields without overwriting rule-derived values. Two pipelines may use the same `DeepWisdom` contract with different settings.

In the mission request body, `customer` supplies `requestingUnit` and `displayName`; `profile_name` supplies `modelName`; `username` falls back to `XUserName` only when null. `missionName` combines the rule's Hebrew name with the image date formatted `dd/MM/yyyy` using invariant culture. The matched rule's own location supplies `focusedWkt`, independently of the input ROI. The caller passes it as `RuleLocationWkt` on the context, from the rule's `match.locationWkt`, so the polygon is stored once. `ValidateRuleLocation` rejects a DeepWisdom rule without a location when rules load; a context without one is also rejected. Optional `origin`, `queueType` and `saveDetections` values come from `ExtraData`.

`tasksData` contains one task with `imageId`. When `run_every_other_image` is true, its nullable `legId`, `prevOverlayId` and `nextOverlayId` come from the overlay. When `should_check_in_vip` is true, `photoTime` is assigned. Unassigned nullable properties are serialized as null. These flags describe downstream behavior; the builder does not perform alternating-image filtering or VIP checks.

The factory stores the photographed legacy `DateTime.Parse(..., InvariantCulture)` result as `OverlayPhotoTime`, independently of the UTC `PhotoTime` used by FindAir. DeepWisdom prefers that clock value and otherwise uses `PhotoTime.DateTime` without another UTC conversion. Offset-bearing input follows the process timezone when parsed; matching the old deployment's timezone preserves its calendar-day behavior. A null Hebrew rule name retains the leading-space mission name rather than inventing a fallback.

## SarAtc

One SarAtc run-parameter object names the model and the fields to filter:

```json
{
  "modelName": "replace-me-model",
  "fieldsToFilter": [ { } ]
}
```

`modelName` is a required nonempty string, with no fixed list of models. `fieldsToFilter` is a required array of JSON objects and may be empty; the contract does not look inside the objects and writes the array to the body as stored, without escaping non-ASCII text. Unknown and duplicate run parameters are rejected. Rules may omit a location; when they set one it only filters images, because the body has no ROI.

The body is `{"imageId", "modelName", "fieldsToFilter", "requestId"}`. `requestId` is the dispatch ID (the context's `TaskId`), so a retried dispatch sends the same value and it matches the outgoing message ID. The only header is `sar-atc-contract-version`, an **integer** `1` in `RabbitMqAttributes`. Context validation needs only the image and dispatch IDs.

Roberto, warmup, HTTP status handling, retries, rule snapshots and dispatch are outside this library. The contract prepares bytes only.
